# gitwire

**중앙 서버 없이 git 레포를 전송 계층으로 쓰는 파이썬 라이브러리.**

각 참가자가 자기 로컬에서 프로세스를 띄우고, 공유 git 레포(private)를 통해
**append-only 레코드**를 주고받는다. 서버 운영이 0이고, 네트워크는 egress
(`pull`/`push`)만 쓴다 — 인바운드가 막힌 환경(사내 방화벽, 노트북, CI 러너,
집 PC)에서도 그대로 동작한다.

```
참가자 A ──push──▶ ┌──────────────┐ ◀──push── 참가자 B
참가자 A ◀──pull── │ private repo │ ──pull──▶ 참가자 B
                   └──────────────┘
                    (레코드 파일들)
```

이건 **기반 프레임워크**다. 그 위에 채팅·칸반 같은 파생 서비스가 얹힌다.

---

## ⚠️ 가장 중요한 설계 경계 — 기반은 "메시지"를 모른다

레코드는 **불투명한 JSON**이다. `author`·`text` 같은 필드를 gitwire 가 알면
그건 전송 계층이 아니라 채팅 라이브러리다. 스키마는 **소비자가 정한다.**

gitwire 가 아는 것은 봉투(envelope)뿐이다:

```json
{"gitwire":1,"id":"records/20260903/...json","sender":"alice.laptop",
 "ts":"2026-09-03T10:11:12.123Z","payload":{ "여기는 소비자 마음대로": true }}
```

`sender` 조차 "누가 말했나"가 아니라 **어느 참가자 프로세스가 발행했나**라는
전송 수준 식별자다(IP 주소에 가깝다). 표시용 신원이 필요하면 소비자가 자기
스키마로 `payload` 안에 담는다.

## 설치

의존성은 **표준 라이브러리뿐**이다. git 은 `subprocess` 로 부른다.

```bash
pip install -e .
```

## 라이브러리로 쓰기

소비자는 두 모양 중 하나다. **둘 다 1급으로 지원하며 같은 디스크 커서를 쓴다.**

### 상시 구독형 (웹앱 백엔드처럼 루프를 도는 프로세스)

```python
import gitwire

ch = gitwire.open_channel(
    "https://github.com/me/my-room.git",
    credential=gitwire.TokenCredential.from_env("GITWIRE_TOKEN"),
)

ch.append({"kind": "msg", "body": "안녕"})       # 발행
sub = ch.subscribe(lambda rec: print(rec.payload))  # 새 레코드만 콜백으로
...
sub.stop()
```

### 일회성 조회형 (에이전트가 셸에서 한 번 부르고 끝나는 프로세스)

브라우저도, 상시 루프도 전제하지 않는다.

```python
ch = gitwire.open_channel("https://github.com/me/my-room.git")
for rec in ch.fetch_new():        # "지난번 이후 새 레코드를 지금 달라"
    handle(rec.payload)
```

마지막 처리 지점은 디스크에 남으므로 **매번 새 프로세스로 실행해도 중복·유실이
없다.** 처리 성공을 직접 확정하고 싶으면:

```python
recs = ch.peek_new()              # 커서를 안 움직이고 본다
...
ch.ack_through(recs[-1].id)       # 처리한 데까지만 전진
```

## CLI 로 쓰기 (에이전트·셸 소비자)

```bash
python -m gitwire init   --repo https://github.com/me/room.git --name "우리 방"
python -m gitwire append --repo ... --payload '{"kind":"msg","body":"안녕"}'
python -m gitwire fetch  --repo ... --consumer agent
```

| 커맨드 | 하는 일 |
|---|---|
| `init` | 빈 레포에 규약(디렉토리 + 첫 커밋)을 심는다. 주소만 넣으면 방이 된다 |
| `status` | 채널·커서 상태 + 원격 SHA 조회 |
| `fetch` | 지난번 이후 새 레코드 (기본: 커서 전진). `--limit` `--no-advance` `--from-now` `--ndjson` |
| `history` | 커서와 무관하게 읽기 (`--limit N` 은 최근 N건) |
| `append` | 레코드 발행. `--payload JSON` 또는 `--payload-file -`(stdin) |
| `ack` | `--record-id` 까지 커서 전진 (`fetch --no-advance` 와 짝) |
| `watch` | 상시 구독 → NDJSON 스트림 (`--max-records` 로 N건 뒤 종료) |
| `compact` | 히스토리 압축 (파괴적, `--yes` 필수) |
| `where` | 로컬 클론·커서 경로만 출력 (네트워크 접근 없음) |

**출력 규약: stdout 은 언제나 기계용 JSON(UTF-8), 사람용 진단은 전부 stderr.**
플래그로 가르면 호출자가 플래그를 빠뜨린 순간 조용히 깨진다. 스트림으로 가르면
플래그와 무관하게 계약이 성립하고 `2>/dev/null` 한 번이면 순수 JSON 이다.
stdout/stderr 는 UTF-8 로 강제한다 — 윈도우 콘솔 코드페이지(cp949 등)에 따라
바이트가 달라지거나 이모지에서 죽으면 기계용 계약이 아니다.

**종료코드 계약** — 셸에서 바로 분기할 수 있다:

| 코드 | 뜻 |
|---|---|
| `0` | 성공 (`fetch` 계열은 **새 레코드 1건 이상**) |
| `10` | 성공했지만 **새 레코드 없음** |
| `2` | 사용법 오류 / 잘못된 payload / 미확인 파괴적 동작 |
| `3` | 자격증명 없음·인증 실패 |
| `4` | git·네트워크 실패 |
| `5` | 채널 초기화 실패 |
| `6` | 원격 히스토리 재작성 충돌 (미푸시 레코드 보호를 위해 중단) |
| `1` | 그 밖의 오류 |

```bash
if python -m gitwire fetch --repo "$REPO" --consumer agent > new.json; then
    process new.json
elif [ $? -eq 10 ]; then
    echo "새 레코드 없음"
fi
```

**대화형 입력을 절대 요구하지 않는다.** 자격증명이 없으면 되묻지 않고 즉시
exit 3 으로 실패한다 — 비대화 환경에서 무한 대기하는 것이 최악의 실패 모드다.
git 호출에는 `GIT_TERMINAL_PROMPT=0` 이 항상 걸린다.

## 왜 이렇게 설계했나

### 변경 감지 — `ls-remote` 로 먼저 묻고, 다를 때만 `pull`

실측: `git ls-remote origin HEAD` = **613~646ms · 46바이트**, `fetch`(변경
없을 때) = **718~752ms**. 30초 주기면 하루 약 130KB. 조용한 채널일수록 이
선판정이 이득이다. 브랜치와 HEAD 를 **한 번의 왕복**으로 같이 묻는다.

### 레코드 1건 = 파일 1개

`records/<날짜>/<타임스탬프>-<발신자>-<랜덤>.json`.

서로 다른 파일이라 **동시 발행해도 내용 머지 충돌이 원천적으로 없다.** 공유 로그
파일 하나를 편집하는 방식은 쓰지 않는다. push 가 거부되면(선점) `fetch` +
`rebase` 후 재시도하며, 파일이 겹치지 않으므로 rebase 는 항상 성공한다.
날짜 디렉토리로 샤딩해 한 디렉토리가 무한히 커지지 않게 했고, 고정폭
타임스탬프가 앞에 오므로 **경로 사전식 정렬 = 시간순 정렬**이다.

### "새 레코드"의 판정 — 커밋 SHA diff + 디스크 커서

커서(`cursors/<소비자>.json`)에 세 값을 둔다:

* `commit` — 마지막으로 배치를 계산한 **기준 커밋**
* `batch_head` + `batch_pos` — 진행 중인 배치의 목표 커밋과 몇 개까지 줬는지
* `watermark` — 지금까지 준 레코드 ID 의 최대값

정상 경로는 `git diff --name-only <commit>..<head> -- records/` 다. 배치는
**결정론적으로 재계산**되므로, 프로세스가 중간에 죽어도 같은 기준에서 같은 배치를
다시 만들어 앞의 `batch_pos` 개를 건너뛰면 정확히 이어진다 → **중복도 유실도 없다.**
커서는 **레코드 한 건을 넘길 때마다** 원자적으로 저장된다.

기준 커밋이 원격에서 사라졌으면(압축·force-push) 전량 나열 후 `watermark`
초과분만 주는 폴백으로 자동 전환한다.

커서는 **소비자별**로 나뉜다 — 같은 방을 웹앱과 에이전트가 각자의 속도로 읽을 수 있다.

### 배칭 — 커밋 폭증 억제

`append()` 는 파일을 **즉시** 디스크에 쓰고(내구성), 커밋·push 는 짧은 창
(기본 3초) 안의 여러 건을 묶어 한 커밋으로 내보낸다. 10건을 연달아 발행하면
커밋은 10개가 아니라 1개다. `flush=True` 나 `flush()` 로 즉시 밀 수 있고,
CLI 는 일회성 호출이 기본이라 배칭 창을 0으로 둔다.

### 공통 시계 — 로컬 시계를 믿지 않는다

파일명·타임스탬프를 작성자 로컬 시계로 찍으면 참가자 간 시계 차이로 순서가
뒤집힌다. 실측: `curl -sI https://github.com` 의 `Date` 헤더 vs 로컬 시계 =
**2.1초 차이**.

그래서 **이미 통신하고 있는 git 호스트의 HTTP `Date:` 응답 헤더**를 기준으로
오프셋을 구한다. 외부 의존이 0이고(NTP·추가 서비스 불필요), 모든 참가자가 같은
호스트를 보므로 자동으로 공통 기준이 된다.

* `Date` 는 **초 단위 절삭**이라 참값은 `[D, D+1)` 에 균등분포한다 → 점추정은 `D+0.5`.
* 요청 직전/직후 로컬 시각의 **중점**을 서버 시각에 대응시켜 RTT/2 를 상쇄한다.
* 잔여 오차는 대략 ±(0.5 + RTT/2)초.
* **세션 시작 1회 + 15분마다 재측정.** 하드웨어 드리프트는 15분에 수 ms 수준이라
  주기 자체는 여유롭지만, NTP 점프·서스펜드 복귀 같은 계단형 변화는 언제든
  생기므로 "1회 측정 후 영구 사용"은 위험하다.
* 측정 실패는 **치명적이지 않다** — 오프셋 0(로컬 시계)으로 degraded 동작한다.
  시계 보정 실패로 전송이 멈추면 안 된다.

### 다중 채널 폴링 — 채널당 독립 스레드

`ls-remote` 비용은 CPU 가 아니라 **네트워크 왕복 대기**다. 순차로 돌리면
채널 20개에 한 라운드 13초(30초 주기의 절반)를 대기로 태우고, 한 호스트가
느려지면 뒤의 모든 채널이 함께 밀린다(head-of-line blocking).

그래서 **채널마다 독립 폴링 스레드**를 쓴다. git 은 subprocess 라 대기 중 GIL 을
잡지 않으므로 파이썬 스레드로도 실제 병렬 왕복이 된다. 채널 하나 안에서는 같은
작업 사본을 만지므로 락으로 직렬화한다 — 병렬성은 **채널 간**에만 준다.

일회성 소비자(`Hub.fetch_new_all()`, CLI)는 반대로 **순차**다. 한 번 실행하고
끝나는 프로세스에서는 스레드 기동·정리 비용이 이득보다 크다.

### 클론 위치

사용자가 볼 일이 없는 앱 상태 저장소다. OS 관례를 따른다:

| OS | 위치 |
|---|---|
| Windows | `%LOCALAPPDATA%\gitwire\channels\<slug>-<hash12>\` |
| macOS | `~/Library/Application Support/gitwire/channels/...` |
| Linux | `$XDG_DATA_HOME`(기본 `~/.local/share`)`/gitwire/channels/...` |

**캐시가 아니라 데이터 디렉토리를 쓴다** — 커서와 아직 push 되지 않은 레코드가
여기 있어서, 캐시 청소 도구가 지워도 되는 데이터가 아니다. 디렉토리 이름은
정규화한 URL의 `sha256` 앞 12자리에 사람이 알아볼 slug 를 붙인 것이라,
**같은 URL 이면 어느 프로세스에서 열든 같은 클론·같은 커서**를 가리킨다
(그래서 일회성 CLI 호출을 반복해도 상태가 이어진다). `GITWIRE_HOME` 으로
통째로 덮어쓸 수 있다.

### 자격증명

* **채널마다 다른 토큰**을 줄 수 있다(다른 조직 레포). 전역 하나로 두면 막힌다.
* 값은 **로컬 프로세스 안에만** 있는다. gitwire 는 토큰을 저장하지 않는다 —
  저장 책임은 호출자(환경변수·OS 키체인·시크릿 매니저)에게 있다.
* URL 에 토큰을 박지 않는다(`.git/config` 에 평문으로 남는다). `GIT_ASKPASS`
  헬퍼 + 환경변수로 넘긴다 — 프로세스 인자(`ps` 노출)에도 git config 에도
  남지 않고, 헬퍼 스크립트 파일 자체에도 토큰이 없다.
* 로그·예외·반환값에 절대 싣지 않는다. 모든 git 출력은 레닥션을 거친다.

### 히스토리 관리 — v1 범위

커밋은 계속 늘어난다. 하지만 **git 히스토리 자체는 이 서비스에 중요하지 않다 —
레코드 파일이 곧 기록이다.** 두 수단을 제공한다:

1. **shallow clone** (`depth=N` / `--depth N`) — 옵트인이지만 **안전한 쪽**이다
   (기본값은 전체 클론). 파괴적이지 않고 내 로컬 비용만 줄인다 — 다른 참가자에게
   아무 영향이 없다. 다만 조상 관계를 로컬에서 판정할 수 없으므로 "여기까지
   push 됨"을 로컬 ref(`refs/gitwire/pushed`)로 따로 표시해 미푸시 여부를 판단한다.

2. **압축**(`compact()` / `gitwire compact --yes`) — 최근 N건만 남긴 단일
   커밋으로 재작성 후 force-push. **파괴적이다.**

   압축의 위험은 "다른 참가자의 미푸시 레코드가 날아간다"는 것이다. 이렇게 다룬다:

   * **자동·주기 실행 경로를 아예 두지 않았다.** `confirm=True`(CLI 는 `--yes`)
     없이는 호출 자체가 거부된다. v1 에서 압축은 **사람이 의도적으로 부르는 도구**다.
   * 압축하는 쪽은 자기 미푸시분을 먼저 flush 한다.
   * 재작성을 만난 다른 참가자는, 미푸시 커밋이 없으면 조용히 `reset` 해서
     따라가고, **미푸시 커밋이 있으면 그것만 새 히스토리 위로 옮겨 심는다**
     (`rebase --onto`). 레코드가 서로 다른 파일이라 충돌이 없다.
   * 그마저 불가능하면 **말없이 버리지 않고** `HistoryRewritten` 을 올린다.
     사람이 `flush()` 하거나 `recover(discard_local=True)` 를 명시적으로 부르게 한다.

   즉 v1 의 입장은 "압축은 제공하되 기본값은 아니다. 자동으로 남의 데이터를
   지우는 경로는 만들지 않는다"이다.

## 정직한 한계

이 설계가 **못 하는 것**들이다. 소비자를 만들기 전에 반드시 읽어라.

* **실시간이 아니다.** 지연 = 폴 주기다. 기본 30초면 최악 30초 + pull 시간이
  걸린다. 주기를 줄이면 그만큼 요청이 늘어난다(호스트 rate limit 주의).
* **진짜 push 가 없다.** 서버가 우리를 깨워주지 않는다. 전부 폴링이다.
  "새 메시지 알림"류는 이 위에서 폴 주기만큼 늦게 뜬다.
* **히스토리가 계속 늘어난다.** 레코드마다 커밋이 쌓인다. shallow clone 과
  압축으로 완화하지만, 압축은 파괴적이라 기본이 아니다. 아주 활발한 채널을
  아주 오래 굴리면 레포가 커진다.
* **레포 접근권 = 참여권이다.** 세밀한 권한이 없다. 읽기만 주거나 특정 레코드만
  가리는 것이 불가능하다. 그리고 **나중에 초대한 사람이 과거 레코드를 전부 본다.**
  git 히스토리 전체가 그대로 넘어가기 때문에, "이 시점부터만 보여주기"가 안 된다.
  민감한 대화에는 맞지 않는다.
* **레코드 삭제가 사실상 안 된다.** append-only 다. 지우려면 히스토리 재작성
  (압축)이 필요하고 그건 모든 참가자에게 파괴적이다.
* **참가자 수가 늘면 push 경합이 커진다.** 선점 시 rebase 후 재시도하므로
  정확성은 유지되지만, 동시 발행이 잦을수록 재시도가 늘어난다. 수십 명이 초 단위로
  쏟아붓는 용도는 아니다.
* **순서는 근사치다.** 공통 시계로 ±1초 안쪽까지 맞추지만 전역 전순서(total
  order)를 보장하지 않는다. 같은 초에 발행된 두 레코드의 상대 순서는 임의다.
* **크래시 시점에 따라 재전달이 있을 수 있다.** 커서는 콜백이 성공한 **뒤에**
  저장된다. 콜백 실행 도중 프로세스가 강제 종료되면 그 한 건이 다음 실행에서
  다시 온다. 소비자 쪽 처리는 **멱등(idempotent)** 하게 만들어라.
* **레코드 크기.** git 이 감당하는 만큼이 한계다. 큰 바이너리는 넣지 마라
  (레포가 영구히 무거워진다).

## 개발

```bash
python -m pytest -q
```

핵심 검증은 **로컬 bare 레포를 원격으로 삼은 2-클론 왕복**이다. 대역이 아니라
**실제 git** 으로 돌린다 — push 거부·rebase·`ls-remote` 같은 것들은 흉내내면
아무것도 증명하지 못한다. 네트워크·git 호출은 주입 가능하므로 단위 테스트는
네트워크 없이 돈다.

파일은 UTF-8(BOM 없음)·LF 로 쓴다.
