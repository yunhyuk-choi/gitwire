# gitwire

**중앙 서버 없이 git 레포를 전송 계층으로 쓰는 파이썬 라이브러리.**

각 참가자가 자기 로컬에서 프로세스를 띄우고, 공유 git 레포(private)를 통해
**append-only 레코드**를 주고받는다. 서버 운영이 0이고, 네트워크는 egress
(`pull`/`push`)만 쓴다 — 인바운드가 막힌 환경(사내 방화벽, 노트북, CI 러너,
집 PC)에서도 그대로 동작한다.

```
참가자 A ──push──▶ ┌──────────────┐ ◀──push── 참가자 B
참가자 A ◀──pull── │ private repo │ ──pull──▶ 참가자 B
                   └──────────────┘
                    (레코드 파일들)
```

이건 **기반 프레임워크**다. 그 위에 채팅·칸반 같은 파생 서비스가 얹힌다.

---

## ⚠️ 가장 중요한 설계 경계 — 기반은 "메시지"를 모른다

레코드는 **불투명한 JSON**이다. `author`·`text` 같은 필드를 gitwire 가 알면
그건 전송 계층이 아니라 채팅 라이브러리다. 스키마는 **소비자가 정한다.**

gitwire 가 아는 것은 봉투(envelope)뿐이다:

```json
{"gitwire":1,"id":"records/20260903/...json","sender":"me@example.com.a3f9c1",
 "ts":"2026-09-03T10:11:12.123Z","payload":{ "여기는 소비자 마음대로": true }}
```

`sender` 조차 "누가 말했나"가 아니라 **어느 설치본이 발행했나**라는 전송 수준
식별자다(IP 주소에 가깝다). 표시용 신원이 필요하면 소비자가 자기 스키마로
`payload` 안에 담는다. 기본값을 어떻게 만드는지는 아래 "설치본 식별자" 참조.

## 라이브러리로 쓰기

소비자는 두 모양 중 하나다. **둘 다 1급으로 지원하며 같은 디스크 커서를 쓴다.**

### 상시 구독형 (웹앱 백엔드처럼 루프를 도는 프로세스)

```python
import gitwire

ch = gitwire.open_channel(
    "https://github.com/me/my-room.git",
    credential=gitwire.TokenCredential.from_env("GITWIRE_TOKEN"),
)

# 발행 = **대기열에 넣기**. 시각·ID 는 원격에 push 되는 순간에 정해진다.
ticket = ch.append({"kind": "msg", "body": "안녕"})
rec = ticket.wait(30)                             # 나가면 그 Record (못 나가면 None)
print(rec.id, rec.sender, rec.timestamp)          # 되파싱할 필요가 없다
sub = ch.subscribe(lambda rec: print(rec.payload))  # 새 레코드만 콜백으로
...
sub.stop()
```

### 일회성 조회형 (에이전트가 셸에서 한 번 부르고 끝나는 프로세스)

브라우저도, 상시 루프도 전제하지 않는다.

```python
ch = gitwire.open_channel("https://github.com/me/my-room.git")
for rec in ch.fetch_new():        # "지난번 이후 새 레코드를 지금 달라"
    handle(rec.payload)
```

마지막 처리 지점은 디스크에 남으므로 **매번 새 프로세스로 실행해도 중복·유실이
없다.** 처리 성공을 직접 확정하고 싶으면:

```python
recs = ch.peek_new()              # 커서를 안 움직이고 본다
...
ch.ack_through(recs[-1].id)       # 처리한 데까지만 전진
```

### 과거로 거슬러 읽기 (역방향 페이징)

"이전 불러오기"·무한 스크롤처럼 **뒤로 가는** 소비자를 위한 표면이다.

```python
page = ch.history_page(limit=50, fresh=False)          # 최신 50건 (로컬만)
while page.has_more:                                   # 종료 조건을 소비자가 알 수 있다
    page = ch.history_page(before=page.oldest, limit=50, fresh=False)  # 그 앞 50건
```

`history(before=..., limit=N)` 는 레코드 리스트만, `history_page()` 는 거기에
`has_more` 를 얹어 준다. ID 만 필요하면 `record_ids(before=..., limit=N)`
(payload blob 을 열지 않는다). 나열 결과는 sha 로 캐시되므로 같은 상태를 반복
조회하면 git 호출이 0회다 — 상태는 `channel.cache_info()` 로 볼 수 있다.

**`fresh=` — 지금 신선도가 필요한가.** 세 읽기 API(`history` · `history_page` ·
`record_ids`)가 모두 받는다. `fresh=True`(기본, 하위호환)는 `ls-remote` 로 원격을
먼저 확인하고, `fresh=False` 는 **로컬 클론만** 읽어 원격 왕복을 0회로 만든다.
실측 차이가 **왕복 1.3초 대 0**이라 이 선택이 곧 체감 성능이다 — 근거와 언제
무엇을 골라야 하는지는 아래 「읽기는 원격을 볼 필요가 없다」.

**keyset 커서다 — offset(`skip=100`) 이 아니다.** 위로 읽는 도중 새 레코드가
도착하면 offset 방식은 경계가 밀려 **같은 레코드를 두 번 주거나 빠뜨린다.**
레코드 ID 는 이미 고정폭 타임스탬프로 시작해 사전식 정렬 = 시간순이므로,
ID 자체가 밀리지 않는 커서가 된다.

### 참가자별 **가변** 상태 (`participants/` — 레코드가 아니다)

"지금 값"을 담는 좁은 창구다. 레코드가 사건이라면 이쪽은 **참가자의 현재 상태**다
(읽음 위치·표시 이름 같은 것). 소비자가 필요해서 열어 둔 예약 경로이며, 기반은
값 안을 해석하지 않는다 (레코드와 같은 경계).

```python
ch.write_state("me@example.com", {"cursor": "records/20260908/….json"})  # 덮어쓴다
ch.read_states()          # {키: ParticipantState} — 참가자 전부
ch.read_state("bob@example.com")                     # 한 명
ch.state_exists("me@example.com")                    # 로컬 stat 한 번 (git 0개)
ch.state_path("me@example.com")   # 'participants/me@example.com.json'
```

⚠️ **자기 키에만 쓴다.** 그 규율이 이 API 의 안전성 근거다 — 아래
「참가자별 가변 상태」 참조. 기반은 키가 누구 것인지 알 수 없어 검사하지 않는다.

## CLI 로 쓰기 (에이전트·셸 소비자)

```bash
python -m gitwire init   --repo https://github.com/me/room.git --name "우리 방"
python -m gitwire append --repo ... --payload '{"kind":"msg","body":"안녕"}'
python -m gitwire fetch  --repo ... --consumer agent
```

| 커맨드 | 하는 일 |
|---|---|
| `init` | **빈 레포**에 규약(디렉토리 + 첫 커밋)을 심는다. 주소만 넣으면 방이 된다 (내용이 있는 레포는 거부한다 — 아래 「빈 레포만」) |
| `status` | 채널·커서 상태 + 원격 SHA 조회 |
| `fetch` | 지난번 이후 새 레코드 (기본: 커서 전진). `--limit` `--no-advance` `--from-now` `--ndjson` |
| `history` | 커서와 무관하게 읽기. `--limit N` `--before <레코드ID>` 로 역방향 페이징 (응답에 `oldest`·`has_more`). `--local` 이면 원격을 보지 않고 로컬 클론만 읽는다 |
| `append` | 레코드 발행 (**항상 push 까지**). `--payload JSON` 또는 `--payload-file -`(stdin). 응답에 `id`·`sender`·`ts` |
| `ack` | `--record-id` 까지 커서 전진 (`fetch --no-advance` 와 짝) |
| `watch` | 상시 구독 → NDJSON 스트림 (`--max-records` 로 N건 뒤 종료) |
| `archive` | **지난 날짜를 로컬 아카이브 파일로 옮긴다** (커밋 없음). `--grace-hours` `--day` `--force` · `--drop` 을 주면 레코드 삭제까지 커밋·push 한다 (합의 판정은 소비자 몫) |
| `recover-archive` | **지워진 날짜를 히스토리에서 꺼내** 로컬 아카이브를 복구한다. `--day` `--through` `--max-days` |
| `compact` | 히스토리 압축 (파괴적, `--yes` 필수) |
| `where` | 로컬 클론·커서 경로만 출력 (네트워크 접근 없음) |

**출력 규약: stdout 은 언제나 기계용 JSON(UTF-8), 사람용 진단은 전부 stderr.**
플래그로 가르면 호출자가 플래그를 빠뜨린 순간 조용히 깨진다. 스트림으로 가르면
플래그와 무관하게 계약이 성립하고 `2>/dev/null` 한 번이면 순수 JSON 이다.
stdout/stderr 는 UTF-8 로 강제한다 — 윈도우 콘솔 코드페이지(cp949 등)에 따라
바이트가 달라지거나 이모지에서 죽으면 기계용 계약이 아니다.

**종료코드 계약** — 셸에서 바로 분기할 수 있다:

| 코드 | 뜻 |
|---|---|
| `0` | 성공 (`fetch` 계열은 **새 레코드 1건 이상**) |
| `10` | 성공했지만 **새 레코드 없음** |
| `2` | 사용법 오류 / 잘못된 payload / 미확인 파괴적 동작 |
| `3` | 자격증명 없음·인증 실패 |
| `4` | git·네트워크 실패 |
| `5` | 채널 초기화 실패 |
| `6` | 원격 히스토리 재작성 충돌 (미푸시 레코드 보호를 위해 중단) |
| `1` | 그 밖의 오류 |

```bash
if python -m gitwire fetch --repo "$REPO" --consumer agent > new.json; then
    process new.json
elif [ $? -eq 10 ]; then
    echo "새 레코드 없음"
fi
```

**대화형 입력을 절대 요구하지 않는다.** 자격증명이 없으면 되묻지 않고 즉시
exit 3 으로 실패한다 — 비대화 환경에서 무한 대기하는 것이 최악의 실패 모드다.
git 호출에는 `GIT_TERMINAL_PROMPT=0` 이 항상 걸린다.

## 왜 이렇게 설계했나

### 변경 감지 — `ls-remote` 로 먼저 묻고, 다를 때만 `pull`

실측: `git ls-remote origin HEAD` = **613~646ms · 46바이트**, `fetch`(변경
없을 때) = **718~752ms**. 30초 주기면 하루 약 130KB. 조용한 채널일수록 이
선판정이 이득이다. 브랜치와 HEAD 를 **한 번의 왕복**으로 같이 묻는다.

⚠️ 저 613ms 는 인증이 캐시된 조건의 값이다. 실제 환경(Windows 11 · git 2.51 ·
GitHub private repo)에서 **자격증명 헬퍼까지 포함한 왕복은 1.3초**다 — 분해는
아래 「자격증명 조회 비용」.

### 읽기는 원격을 볼 필요가 없다 (`fresh=`)

예전에는 `history()` · `history_page()` · `record_ids()` 가 **매 호출** `sync()`
를 탔다. 즉 "이전 50건 보여줘" 한 번에 `ls-remote` 왕복이 한 번씩 붙었다.
실측(같은 머신·같은 레포, 5회 중앙값):

| | 시간 |
|---|---|
| `git ls-remote origin refs/heads/main HEAD` | **1320 ms** |
| 로컬 나열 `git ls-tree -r --name-only HEAD` | **44 ms** |

그럴 이유가 없다. **채널은 클론이다 — 레코드는 이미 로컬에 있다.** 원격에
물어봐야 알 수 있는 것은 "그 뒤에 새 것이 더 있나" 하나뿐이고, 그건 이미
**구독(`subscribe`)** 이 주기마다 하고 있다. 읽기까지 원격을 보면 같은 일을 두
곳에서 한다. 특히 **과거로 거슬러 올라가는 페이징은 원격과 아예 무관하다** —
이미 받은 커밋 안에서 뒤로 가는 것이기 때문이다.

그래서 세 읽기 API 에 `fresh=` 를 두어 **소비자가 고르게** 했다. 기본값은
`True`(기존 동작 그대로)이고, `fresh=False` 가 로컬 전용 모드다.

### 락은 로컬을 바꾸는 동안만 쥔다

읽기에서 원격을 떼고도 조회가 1.5초씩 걸리는 일이 남아 있었다. 이유는 `sync()`
가 `ls-remote`(1.3초) 내내 채널 락을 쥐고 있었고, **읽기 경로도 같은 락을 쓰기**
때문이다 — 조회 자체는 40ms 인데 폴러 뒤에 줄을 서 있었다.

그래서 락 범위를 좁혔다. `has_changes()`(= ls-remote)는 로컬 상태를 건드리지
않으므로 **락 밖**에서 하고, 실제로 로컬을 바꾸는 `fetch` + `integrate` 만 락
안에서 한다(그 사이 다른 스레드가 먼저 당겼을 수 있으므로 락 안에서 한 번 더
판정한다 — 헛돌아도 정확성에는 영향이 없다). 커서 경로(`fetch_new` ·
`poll_once` · `skip_to_now`)도 `sync()` 를 락 밖에서 먼저 돌린다.

실측(소비자 앱의 `GET /api/rooms/<id>/messages?limit=50`, 진짜 GitHub 원격):
**1463ms → 51ms**. 락을 좁히기 전에는 읽기를 로컬로 바꾼 뒤에도 1524ms 였다.

#### 같은 실수가 `flush()` 에 남아 있었다 — push 도 락 밖으로

`sync()` 를 고친 뒤에도 **전송이 2.8초** 걸렸다. 소비자가 `flush=True` 를 떼고
배경 아웃박스로 옮겼는데도 **첫 건만 빨라지고 2번째부터 다시 느렸다.** 원인은
같은 종류였다 — `flush()` 가 push 가 끝날 때까지 채널 락을 쥐고 있었고, 그 락은
`append()` 와 모든 읽기가 함께 쓴다. 배경 push 가 도는 2.7초 동안 **다음 보내기와
조회가 통째로 줄을 섰다.**

그래서 락을 둘로 갈랐다. **순서는 언제나 `_remote` → `_lock`** 이고 그 반대는 없다:

| 락 | 지키는 것 | 누가 쓰나 |
|---|---|---|
| `_lock` (채널 락) | 작업 사본·인덱스·발행 대기열·커서·캐시 — **짧은 로컬 구간** | `append()` · 모든 읽기 · 그리고 아래 원격 전이의 *로컬 부분만* |
| `_remote` | "원격 상태 전이"(커밋 → push → fetch → 통합) 전체 — **네트워크를 여기서 기다린다** | `flush()` · `sync()` · `drop_days()` · `recover()` · `compact()` |

`flush()` 는 찍기·커밋까지만 채널 락 안에서 하고, push 는 `_remote` 만 쥔 채 락
밖에서 기다린다. push 중에 들어오는 `append()` 는 **메모리 대기열에만** 붙으므로
작업 사본·인덱스·HEAD 를 한 바이트도 건드리지 않고, 그 건들은 다음 flush 가 가져간다.
읽기는 커밋 기준이라 영향이 없다. 진짜 위험한 것은 *다른 원격 전이*(`sync()` 의
통합·레코드 삭제·`compact()`)가 push 도중 끼어들어 방금 올린 커밋을 로컬에서 갈아치우는
경우인데, 그것들이 전부 `_remote` 를 거치므로 겹치지 않는다.

그리고 **push 는 명시적인 sha 를 민다**(`HEAD:` 가 아니라). 락 밖에서 `HEAD:` 로
밀면 무엇을 올렸는지가 push 시점에야 정해지고, 뒤이어 "여기까지 올렸다" 표시가
*그 사이 늘어난* 커밋까지 올린 것으로 만들어 **아직 안 올라간 레코드를 조용히
유실**시킬 수 있다.

실측 (Windows 11 · push 2.7초를 흉내낸 원격 · 6건 연속 전송, 그동안 계속 조회):

```
$ python bench_flush.py 2.7          # 고치기 전
  전송 1:     42.4 ms      전송 4:   3429.3 ms
  전송 2:   3307.5 ms      전송 5:   3354.7 ms
  전송 3:   3364.8 ms      전송 6:   3374.4 ms
전송 응답   중앙값=3364.8  최소=42.4    최대=3429.3 ms
push 중 조회 중앙값=3483.5  p95=3536.7  최대=3536.7 ms
원격에 착지: 6/6 · 순서·중복 이상 없음: True

$ python bench_flush.py 2.7          # 고친 뒤
```

**전송 3365ms → 49ms, push 중 조회 3484ms → 46ms.** 6건 전부 원격에 착지했고
중복·순서 이상이 없다 — *빠르기만 하고 유실되면 고친 게 아니다.* 남은 297ms 한
번은 커밋(`git add` + `commit`)이 채널 락을 쥔 구간이고, 이건 로컬 작업이라
락이 필요하다. `tests/test_flush_lock.py` 가 이 성질을 고정한다 (push 중
`append`·읽기가 막히지 않는가 / push 끼리 겹치지 않는가 / push·`sync`·아카이빙·
`compact`·`close` 가 겹칠 때 유실·중복·교착이 없는가).

바뀌는 의미는 정확히 하나다: `fresh=False` 결과는 **마지막 폴 시점** 기준이다.
그러니 신선도가 필요한 순간(예: 방을 지금 막 열었다)에는 소비자가
① `fresh=True` 를 쓰거나 ② 화면을 막지 않고 따로 당기면 된다. 이 성질은
`tests/test_local_reads.py` 가 세 각도로 못 박는다 — 로컬 읽기는 `ls-remote`
0회, 페이지 계약(중복·누락·경계)은 그대로, 그리고 **남이 방금 push 한 것은
폴이 돌기 전까지 안 보인다.**

### 자격증명 조회 비용 — 네트워크 호출에만, OS 저장소로

`ls-remote` 1.3초를 `GIT_TRACE` 로 뜯으면 이렇다 (Windows 11 · git 2.51 ·
GitHub private repo):

* git 이 왕복마다 `git credential-manager get`(그리고 성공 후 `store`)을
  **셸 + .NET 프로세스로 새로 띄운다.**
* `ls-remote` 는 private repo 에 HTTPS 왕복을 **3번** 한다 — ①익명 GET → 401
  ②인증 GET → 200 ③protocol-v2 `ls-refs` POST.

helper 사슬만 바꿔 가며 잰 값 (5회 중앙값):

| helper 사슬 | ls-remote 1회 |
|---|---|
| `manager` (시스템 기본, GCM) | **1320 ms** |
| `cache --timeout=900` → `manager` | **1167 ms** |
| `cache --timeout=900` 단독 (캐시 적중) | **910 ms** |

즉 **GCM 이 왕복당 약 400ms**이고, 남는 ~900ms 는 helper 와 무관한 고정비다
(HTTPS 왕복 3회 + 프로세스 기동). 캐시로 지울 수 있는 것은 1.3초 중 0.4초뿐이다.

#### 지금 기본값 — OS 기본 저장소 헬퍼를 네트워크 호출에만 얹는다

`git-credential-cache` 는 **없는 머신이 있다**(실측: 이 Windows 머신에는
`git-credential-wincred.exe` 만 있고 cache 는 없다). 그래서 기본값은 데몬 캐시가
아니라 **그 OS 가 이미 제공하는 저장소**다 — Windows `wincred` / macOS
`osxkeychain` / Linux `libsecret`.

실측 (`push --dry-run`, 인증이 필요한 GitHub 호출, 5회 중앙값):

| helper | 1회 | `GIT_TRACE` 상 헬퍼 기동 |
|---|---|---|
| 사용자 설정 그대로 (system: `manager` = GCM) | **1,552 ms** | `manager get` + `manager store` |
| `wincred` 단독 | **1,220 ms** | `wincred get` + `wincred store` |
| `wincred` → `manager` (사슬) | **1,519 ms** | + `manager store` ← 되돌아온 비용 |
| 헬퍼 없음 | 540 ms | 없음 — **rc 128, 인증 실패** |

읽을 것이 셋이다:

* ⚠️ **`credential.helper` 는 다중값이다.** `-c credential.helper=X` 만 주면
  기존 사슬에 *추가*되고, git 은 인증 성공 후 `store` 를 **사슬 전원**에게
  보내므로 GCM 비용이 그대로 돌아온다(표 3행). 그래서 **빈 값으로 목록을
  초기화한 뒤** 하나만 지정한다: `-c credential.helper= -c credential.helper=…`.
* ⚠️ **헬퍼를 아예 비우면 제일 빠르지만 깨진다.** 자격증명이 캐시돼 있지 않은
  사람은 push 가 실패한다(rc 128). 그래서 비우지 않는다.
* 한 번의 헬퍼 기동이 `sh.exe` → `git.exe` → 헬퍼로 **3프로세스**다. 그래서
  헬퍼를 바꿔 살 수 있는 것은 왕복당 ~330ms 이고, 남는 ~600ms 는 헬퍼와 무관한
  고정비(HTTPS 왕복 + 프로세스 기동)다.

규칙:

* **네트워크 서브커맨드에만** 얹는다 (`push`·`fetch`·`clone`·`pull`·`ls-remote`).
  로컬 git 호출의 동작은 한 글자도 바뀌지 않는다.
* **사용자의 global·system 설정은 읽지도 고치지도 않는다.** 우리가 띄우는 git
  프로세스의 `-c` 로만 얹는다.
* **그 헬퍼가 없으면 사용자 설정 그대로** 쓴다 (느린 것이 깨지는 것보다 낫다).
  `GITWIRE_CREDENTIAL_HELPER` 로 이름을 강제하거나 `off` 로 끌 수 있다.
* **인증이 실패하면** 그 호출을 사용자 설정으로 한 번 더 시도하고, 이후로는
  접는다 — 자격증명이 GCM 전용 저장소에만 있는 사람도 깨지지 않는다.
* 둘 다 **로그에 남긴다** (조용한 열화 금지).

#### 옵트인 — 데몬 캐시 사슬을 직접 짜고 싶으면

`Channel(credential_helpers=[...])` 를 주면 그 사슬을 **이 클론의
`.git/config`** 에 쓰고(상속된 helper 는 뒤에 남긴다), 위의 기본 지정은
비켜선다. `gitwire.credential_cache(초)` 가 `cache --timeout=…` 한 줄을 만들어
준다 — 단 `git-credential-cache` 가 있는 머신에서만 쓸모가 있고, 자격증명을
데몬 프로세스의 메모리에 그 시간 동안 들고 있는 **거래**다.

### 레코드 1건 = 파일 1개

`records/<날짜>/<타임스탬프>-<발신자>-<랜덤>.json`.

서로 다른 파일이라 **동시 발행해도 내용 머지 충돌이 원천적으로 없다.** 공유 로그
파일 하나를 편집하는 방식은 쓰지 않는다. push 가 거부되면(선점) `fetch` +
`rebase` 후 재시도하며, 파일이 겹치지 않으므로 rebase 는 항상 성공한다.
날짜 디렉토리로 샤딩해 한 디렉토리가 무한히 커지지 않게 했고, 고정폭
타임스탬프가 앞에 오므로 **경로 사전식 정렬 = 시간순 정렬**이다.

### 참가자별 가변 상태 — 예약 경로 `participants/`

레코드는 **사건**이고 절대 수정하지 않는다. 그런데 소비자에게는 사건이 아닌 것도
필요하다 — "이 사람이 지금 어디까지 읽었나" 같은 **현재 값**이다. 그걸 레코드로
적으면 두 가지가 동시에 망가진다:

* 지금 값을 알려면 그 사람의 마지막 갱신까지 **과거로 스캔**해야 한다. 2주 만에
  들어온 사람이면 2주치다 — keyset 페이징으로 없앤 전량 스캔이 되살아난다.
* append-only 규약(한 파일 = 한 사건, 수정 금지)이 흐려진다.

그래서 **개념을 갈라 예약 경로를 하나 둔다.**

```
records/<날짜>/*.json     사건        append-only, 개수가 무한히 늘어난다
archive/<날짜>.jsonl      사건        아카이빙 — 옮긴 것이지 버린 것이 아니다 (**추적되지 않는다**)
participants/<키>.json    현재 값     덮어쓴다, 개수 상한 = 참가자 수
```

`participants/<키>.json` 은 봉투 하나에 불투명한 `value` 를 담는다. 기반은
`value` 안을 해석하지 않는다 — 레코드와 **같은 경계**다.

```json
{"gitwire_state":1,"key":"me@example.com","identity":"me@example.com",
 "updated_at":"2026-09-08T05:11:12Z","value":{ "여기는 소비자 마음대로": true }}
```

#### ⭐ 안전성의 근거 — **경로마다 쓰는 사람이 한 명**

파일 하나 = 참가자 한 명이고, **그 파일을 쓰는 것은 그 참가자뿐이다.** 그래서
서로 다른 참가자의 동시 갱신이 서로 **다른 경로**를 만지고, 동시 push 는 기존
fetch + rebase 재시도 경로가 그대로 처리한다 (겹칠 파일이 없다). 공유 파일 하나에
전원의 값을 담으면 정반대가 된다 — 두 사람이 같이 읽으면 같은 경로를 같이 써서
매번 충돌한다.

⚠️ 이 성질은 **소비자가 지켜야 한다.** 기반은 키가 누구 것인지 알 방법이 없어
(신원은 소비자의 개념이다) 검사하지 않는다. 남의 키에 쓰면 그 순간 근거가 사라진다.

한 사람이 노트북·데스크탑을 함께 쓰면 예외적으로 **같은 경로**를 공유한다. 그
경합이 rebase 충돌 → `HistoryRewritten` 이 되면 **메시지 전송까지 막히므로**,
기반이 해소 규칙을 미리 정해 둔다: 옮겨 심는 쪽(= 지금 push 하려는 우리 값)이
이긴다 (`channel._REBASE_RESOLVE`). 값이 단조 증가여야 하는 소비자는 쓰기 전에
저장된 값을 읽어 `max` 를 취하면 되고, 뒤처진 값이 한 번 이겨도 다음 갱신에서
회복된다. 레코드는 이 규칙에 걸리지 않는다 — 파일명이 겹치지 않기 때문이다.

#### 커밋 대상에 들어간다

예전에는 커밋 스테이징이 `git add -A -- records/` 였다. 그래서 소비자가 클론에
파일을 떨어뜨려도 **커밋에 실리지 않았다** (조용한 유실). 지금은 이 예약 경로가
같은 `git add` 의 pathspec 에 함께 들어가고, 대기 중인 레코드와 **한 커밋**으로
나간다 — 부수 상태의 발행이 메시지 전송보다 앞서 끼어들 수 없다. 예약 경로가
아직 없는 옛 채널에서는 pathspec 에서 조용히 빠진다(없는 경로를 주면 `git add` 가
실패하고, 그러면 같은 호출의 레코드까지 스테이징되지 않는다).

#### 아카이빙·삭제·압축이 건드리지 않는다

`archive_days()`·`drop_days()` 는 `records/` 의 날짜 디렉토리만 만지고,
`compact()` 는 `records/` 만 버린다. 예약 경로는 **레코드가 아니므로** 둘 다 손대지 않는다.

#### 읽기 비용

`read_states()` 는 전량을 그대로 읽는다 — 개수의 상한이 **참가자 수**이고 사건
수와 무관하기 때문이다(레코드가 커서·페이징을 쓰는 이유가 여기서 갈린다).
나열은 커밋 sha 로 캐시되므로 같은 상태를 되풀이 조회하면 **git 호출이 0회**다.
기본값도 `fresh=False`(로컬만)라, 폴 주기마다 값을 다시 읽어도 유휴 비용이
늘어나지 않는다.

### "새 레코드"의 판정 — 커밋 SHA diff + 디스크 커서

커서(`cursors/<소비자>.json`)에 세 값을 둔다:

* `commit` — 마지막으로 배치를 계산한 **기준 커밋**
* `batch_head` + `batch_pos` — 진행 중인 배치의 목표 커밋과 몇 개까지 줬는지
* `watermark` — 지금까지 준 레코드 ID 의 최대값

정상 경로는 `git diff --name-only <commit>..<head> -- records/` 다. 배치는
**결정론적으로 재계산**되므로, 프로세스가 중간에 죽어도 같은 기준에서 같은 배치를
다시 만들어 앞의 `batch_pos` 개를 건너뛰면 정확히 이어진다 → **중복도 유실도 없다.**
커서는 **레코드 한 건을 넘길 때마다** 원자적으로 저장된다.

기준 커밋이 원격에서 사라졌으면(압축·force-push) 전량 나열 후 `watermark`
초과분만 주는 폴백으로 자동 전환한다.

커서는 **소비자별**로 나뉜다 — 같은 방을 웹앱과 에이전트가 각자의 속도로 읽을 수 있다.

### 방으로 만들 수 있는 레포 — **빈 레포만**

`open()` 은 채널이 아닌 레포를 만나면 규약(`gitwire.json` + `records/`)을 심고
**push 한다.** 그 동작이 "주소만 주면 방이 된다"를 성립시키지만, 주소를 잘못 넣으면
*쓰고 있는 코드 레포에 커밋이 올라간다.* 실제로 그렇게 만든 적이 있다 — 인증
실패를 시험하려고 진짜 코드 레포 주소를 넣었더니 `gitwire.json` 이 그 레포 main 에
올라갔다.

그래서 심는 조건을 좁혔다:

* **빈 레포** — 심는다.
* **README·LICENSE·.gitignore·.gitattributes 정도만 있는 레포** — 심는다
  (forge 가 새 레포를 만들 때 넣어 주는 것들이라 "쓰고 있는 레포"가 아니다).
* **그 밖에 내용이 있는 레포** — **아무것도 쓰지 않고** `ChannelInitError` 를 올린다.
  정말 그 레포를 채널로 쓰려면 `gitwire.json` 을 직접 커밋해 두면 된다.

### 설치본 식별자 — `sender` 기본값

`sender` 는 **전역 신원이 아니라 "이 설치본인가"를 가르는 값**이다. 그래서
`<유저>.<호스트>` 로는 안 된다 — **같은 머신의 두 프로세스가 같은 값**이 되고,
그 순간 "이 레코드가 내가 낸 것인가" 판정이 무너진다(남의 레코드를 자기 에코로
오인 → 그 위에 얹은 알림·읽음 처리가 조용히 틀린다).

그래서 설치본마다 한 번 만들어 **디스크에 영속**시킨다:

```
<gitwire_home>/installation.txt      → me@example.com.a3f9c1
```

* 씨앗은 **git 이 이미 아는 신원**(`git config user.email`, 없으면
  `<유저>.<호스트>`) + 짧은 난수다. 사람이 레코드 파일을 눈으로 봐도 누구 것인지
  알아볼 수 있고, 난수가 설치본을 가른다.
* 재시작해도 같다(파일이라서). 설치본 = 하나의 `GITWIRE_HOME` 이다 — 같은 home 은
  어차피 같은 클론·같은 커서라 한 설치본일 수밖에 없다.
* ⚠️ **forge 계정(GitHub 등)에 묶지 않는다.** gitwire 는 GitLab·사내 git·bare·
  로컬 경로를 다 지원하는 forge 중립 설계이고, 무엇보다 forge 계정은 *같은 사람의
  두 머신·두 프로세스를 구별하지 못해* 애초의 버그를 고치지 못한다.
* 명시적으로 넘긴 `sender=`(라이브러리 인자·CLI `--sender`·`GITWIRE_SENDER`)는
  그대로 존중한다. 기존 채널의 기존 레코드도 그대로 읽힌다.

### 역방향 페이징 — 요청한 만큼만 blob 을 연다

레코드는 `records/<날짜>/<id>.json` 이고 ID 는 고정폭 타임스탬프로 시작한다.
그래서 **날짜 디렉토리를 역순으로 훑고, 커서보다 뒤인 날짜는 디렉토리째 건너뛰고,
필요한 개수를 채우면 멈춘다.** 여는 blob 은 딱 요청한 N건이다.

전량을 나열한 뒤 잘라내는 방식은 대화가 길수록 선형으로 느려진다 — 50건을
보여주려고 수천 건을 읽는 것은 페이징이 아니다. `has_more` 는 **한 건을 더
나열해 보고**(blob 은 열지 않는다) 판정한다.

### 나열 캐시 — 키가 sha 라 stale 이 정의상 불가능하다

blob 을 요청한 만큼만 열게 하고 나니 **고정비가 드러났다.** 실측(이 머신):
git subprocess 한 번은 하는 일과 무관하게 **42~48ms** 다 — `rev-parse HEAD`
(47.7ms)나 5000건 전량 나열(48.6ms)이나 같다. 비용은 작업이 아니라 프로세스
기동이다. 한 쪽마다 나열을 2회(날짜 목록 → 그 날짜의 레코드) 하므로 ~90ms 가
바닥으로 깔리고, 무한 스크롤은 이 경로를 반복 호출한다.

그래서 나열 결과를 캐시한다. **무효화 규칙을 두지 않는다** — 대신 git 이 이미
주는 불변식을 쓴다: **git 오브젝트는 내용 주소라 같은 sha 면 내용이 반드시 같다.**

* 날짜 목록은 **커밋 sha**, 각 날짜의 레코드 목록은 그 **날짜 디렉토리의 트리
  sha** 로 캐시한다. 트리 sha 는 `ls-tree` 한 번에 날짜 이름과 **같이 나오므로**
  sha 를 얻는 추가 왕복이 없다. 트리 단위라 더 촘촘하다 — 오늘 날짜에 레코드가
  추가돼도 어제 날짜의 sha 는 그대로라 캐시가 계속 맞는다.
* "지난 날짜는 안 바뀐다" 같은 가정 위에 세우지 않았다. 그 가정은 **틀린다** —
  오프라인에서 쓰고 나중에 push 하거나 시계가 어긋난 참가자는 **과거 날짜에**
  레코드를 추가하고, fetch 로 남의 커밋이 들어오면 과거 트리가 바뀐다. sha 키는
  그 경우 자동으로 다른 키가 되므로 **낡은 값이 나올 수 없다.**
* 메모리 캐시만 둔다. 디스크까지 가면 재시작 후 첫 쪽이 빨라지지만(1회 ~90ms)
  포맷·손상 처리·수명 관리가 늘어난다 — 반복은 한 세션 안에서 일어나므로 값이
  없다고 판단했다.
* 상한은 **담긴 경로 문자열 수**(기본 20000개 ≈ 실측 2.09MB)이고 넘치면 LRU 로
  버린다. 항목 수가 아니라 경로 수인 이유는 하루치가 몇 건이냐에 따라 항목 크기가
  100배씩 달라지기 때문이다. 상한이 필요한 이유는 sha 키의 대가다 — 발행할 때마다
  오늘 날짜의 트리 sha 가 바뀌므로 세션이 길면 항목이 쌓인다. 버려도 정확성에는
  영향이 없다(다음 조회에서 git 을 한 번 더 부를 뿐).

실측(5000건 방에서 50건씩 5쪽 거슬러 올라가기): 쪽당 `ls-tree` **2회 → 0회**
(첫 쪽만 2회), 쪽당 **297ms → 187ms**, 5쪽 합계 **1488ms → 1035ms**.
남은 바닥은 쪽마다 도는 `sync()`(ls-remote 1 + rev-parse 2)였는데, 그건
`fresh=False` 가 없앴다 — 위 「읽기는 원격을 볼 필요가 없다」.

### 유휴 폴링 — 폴링 1회에 git 1개

**아무 일도 없는 방이 분당 몇 MB 를 읽고 있었다.** 실측(2026-09-08 · Windows 11
· git 2.51 · 이 라이브러리를 쓰는 채팅 앱 · 방 1개 · 새 메시지 없음 · 90초):
CPU 는 코어 1개의 0.69%, RSS 54.8MB, 디스크 **쓰기 0** — 멀쩡한데 **디스크
읽기만** 아팠다. 원인은 폴링 한 번에 git 프로세스를 여러 개 띄우는 것이었다.

계측(Job Object 로 프로세스·읽기를 누적 — 짧은 프로세스도 놓치지 않는다):

| 유휴 폴링 1회 | 전 | 후 |
|---|---|---|
| gitwire 의 git 호출 | **7개** | **1개** (`ls-remote`) |
| 실제 프로세스 (git + conhost + 로컬 upload-pack) | 16개 | 3개 |
| 논리 읽기 | 8.96 MB | 1.55 MB |
| 읽기 연산 | 938회 | 223회 |

7개가 무엇이었나 — 그 중 **원격을 봐야 하는 것은 첫 줄 하나뿐**이다:

```
ls-remote origin refs/heads/main HEAD        ← 원격에 물어볼 수밖에 없다
rev-parse --verify --quiet refs/remotes/origin/main
rev-parse --verify --quiet HEAD
cat-file -e <sha>^{commit}                   ┐ `_plan()` — 기준 커밋과 목표
merge-base --is-ancestor <sha> <sha>         │ 커밋이 **같은데도** 도달성·조상
diff --name-only --diff-filter=d -z ...      │ 관계·diff 를 매번 물었다
diff --name-only -z ...                      ┘
```

git subprocess 한 번은 **하는 일과 무관하게 약 494KB 를 읽고 65~73회의 읽기
연산**을 낸다(위 「나열 캐시」의 42~48ms 와 같은 이야기 — 비용은 작업이 아니라
프로세스 기동이다: 바이너리·DLL·설정·인덱스를 매번 다시 읽는다). ⚠️ Windows 에서
콘솔 창을 없애려고 `CREATE_NO_WINDOW` 를 걸었으므로 git 하나마다 **`conhost.exe`
가 함께** 뜬다 — 호출 하나의 값이 두 배다(창 억제를 포기할 이유는 아니다.
호출을 줄이는 이유일 뿐이다).

**적응형 폴링(유휴 시 주기를 늘리기)은 택하지 않았다.** 그건 체감 지연을 파는
것이다. 지연을 그대로 두고 읽기만 줄이는 길이 있으면 그쪽이 먼저다.

두 가지를 고쳤다:

**(1) `_plan()` 의 자명한 경우를 계산하지 않는다.** 기준 커밋과 목표 커밋이 같으면
답이 이미 정해져 있다 — 도달 가능(방금 로컬에서 읽은 커밋이다)·자기 자신의
조상·자기와의 diff 는 공집합. 유휴에서는 **항상** 이 경우다. git 4개가 0개가
된다. (전달 중간에 끊긴 배치가 있으면(`batch_pos > 0`) 예전 경로를 그대로 탄다.)

**(2) 로컬 ref 조회를 메모리에 들고, 두 겹으로 지킨다** (`localrefs.py`).
로컬 HEAD 와 원격추적 ref 는 로컬이 바뀌지 않는 한 바뀌지 않는다. 유휴에서는
아무도 바꾸지 않으므로 매번 물어볼 이유가 없다. 문제는 **틀렸을 때의 증상이
조용하다는 것**이다 — 낡은 HEAD 를 믿으면 새 메시지를 못 보거나 push 가 어긋난다.
그래서 캐시하는 대신 두 겹을 깐다:

* **겹 1 — `.git` 안 ref 파일의 스탬프.** 캐시를 채울 때 `HEAD`·(HEAD 가 가리키는
  ref 파일)·`refs/remotes/origin/<브랜치>`·`packed-refs`·`config` 의 stat 과
  (작은 파일은) **내용**을 함께 적어 둔다. 조회할 때 다시 계산해 **한 바이트라도
  다르면 버리고 git 에게 다시 묻는다.** 계산 비용은 stat 4~5회 + 41바이트 파일
  3개 읽기 = **프로세스 0개**다.
  이 겹이 있어야 **밖에서 클론을 건드리는 경우**를 견딘다 — 사람이 그 클론에서
  직접 `git fetch`·`git reset` 을 돌리는 경우, 그리고 더 흔한 경우로 **같은
  클론을 보는 두 프로세스**(상시 앱 + 셸에서 부른 CLI 는 같은 `GITWIRE_HOME` 을
  공유한다)가 있다. ref 가 바뀌면 파일이 반드시 바뀌므로 즉시 알아챈다 —
  "우리만 로컬을 바꾼다"는 가정에 기대지 않는다. 그 가정은 언젠가 깨지고, 깨졌을
  때의 증상이 *새 메시지가 조용히 안 보이는 것* 이다.
  시각 해상도에 기대지도 않는다: ref 파일은 41바이트라 **내용을 그대로 비교**하므로
  mtime 해상도가 1초인 파일시스템에서도 정확하다. `packed-refs`·`config` 는 클 수
  있어 stat 만 보는데, git 은 이 둘을 임시파일 + rename 으로 통째로 갈아치우므로
  stat 이 반드시 달라진다.
* **겹 2 — 우리가 부르는 모든 git 호출을 한 곳에서 보고 무효화한다.**
  `GuardedRunner` 가 채널의 유일한 git 실행 경로를 감싼다. **읽기 전용
  화이트리스트에 없는 서브커맨드면 무조건 캐시를 버린다** — 모르는 것은 위험한
  쪽으로 분류한다. 무효화 지점을 사람이 하나하나 챙기는 방식이 아니므로 *로컬을
  바꾸는 코드가 새로 생겨도 무효화를 빠뜨릴 수 없다.* 실패한 명령도 무효화한다
  (중단된 rebase 는 로컬을 절반쯤 바꿔 놓는다).

**신뢰할 수 없으면 캐시하지 않는다.** `.git` 이 디렉토리가 아니거나(워크트리·
서브모듈), `reftable` 백엔드를 쓰거나, HEAD 를 읽을 수 없으면 스탬프를 만들지
않고 매번 git 에게 묻는다(예전 동작 — 느릴 뿐 틀리지 않는다). 특히 reftable 은
ref 를 `refs/*` 파일로 두지 않아 스탬프가 영영 그대로일 수 있다 — 그것이 정확히
"조용히 낡는" 경우라 아예 켜지 않는다. 상태는 `channel.local_ref_cache_info()`
로 볼 수 있다(적중·무효화·포기·경합 횟수).

로컬이 실제로 바뀐 직후의 첫 폴은 `rev-parse` 를 한 번 더 부른다 — 캐시를 다시
채우는 값이고, 그때는 정말 물어봐야 한다.

**남은 1개는 줄일 수 없다.** `ls-remote` 는 "원격에 새 것이 있나"를 묻는 유일한
수단이고, 그것을 없애는 길은 폴링을 덜 하는 것(= 체감 지연을 파는 것)뿐이다.

### 레코드의 시각·ID = **원격에 push 되는 순간** (그리고 그 대가)

`append()` 는 **대기열에 넣기만** 한다. 시각을 찍고 ID(= 파일 경로)를 만들고
파일을 쓰고 커밋·push 하는 것은 전부 `flush()` 가 *한 번에, 그 순서로* 한다.
`append()` 가 돌려주는 것은 그래서 `Record` 가 아니라 **티켓**(`PendingRecord`)이고,
실제 레코드는 push 가 확정될 때 그 티켓에 달린다 (`ticket.wait()`).

**왜** — 예전에는 `append()` 가 *작성 시각*으로 ID 를 굳히고 push 는 나중에 했다.
레코드 ID 는 정렬 키이자 커서 값이므로, 오프라인에서 쓴 말이 며칠 뒤에 나가면
**과거 날짜 ID 로 도착**한다. 실측된 결과가 둘이다:

* 안 읽음 카운트가 `|{p ≠ A, cursor(p) < M}|` 이고 커서는 단조 증가라 과거 ID 는
  모두의 커서보다 앞이다 → **아무도 안 봤는데 "전원 읽음"**.
* 화면에서는 며칠 위에 끼워진다 → OS 알림은 오는데 **볼 곳이 없다.**

작성 시각은 **남기지 않는다**(`composed_at` 같은 필드를 두지 않는다). 쓰지 않는
값을 봉투에 넣으면 그때부터 "어느 시각이 정본인가"를 소비자마다 다시 판단한다.

**대가 — 대기열은 메모리다.** "보내고 바로 죽여도 다음 기동이 밀어낸다"는 보장을
버렸다. 강제 종료되면 아직 안 나간 레코드는 사라진다. 그 보장을 지키려면 안 나간
것을 디스크에 남기고 다음 기동이 밀어야 하는데, 그 순간 위의 과거-날짜 결함이
그대로 되살아난다. 대신 **살아 있는 동안**은 지킨다:

* **순서** — 대기열 앞에서부터 한 커밋으로 밀고, 그 push 가 성공할 때까지 뒤 건을
  따로 보내지 않는다. push 가 실패하면 찍은 것을 되돌려(`reset --mixed` + 파일
  삭제) 대기열로 돌려놓고, 다음 시도가 **그때의 시각**을 다시 찍는다.
* **무손실** — 실패는 재시도된다(소비자의 아웃박스가 지수 백오프로 민다).

소비자는 그래서 *아직 안 나간 것*을 "보냈다"로 표시해서는 안 된다. gitwire-chat 은
낙관적 말풍선에 봉투 없는 임시 ID(`~pending/…`)를 주고 *보내는 중…* 으로 그린다 —
사라져도 괜찮은 상태다. "보냈다"는 진짜 봉투가 생긴 뒤에만 말한다.

### 발행은 드레인 루프다 — 타이머가 없다

예전에는 **배칭 창**(기본 3초)이 있었다. 커밋 폭증은 막았지만, 조용한 방에서
한 건을 보내면 그 3초가 **통째로 사용자 지연**이었다 (실측: 한 건 전송
4,018ms 중 3,000ms 가 창).

지금은 창을 없앴다. 규칙이 셋이다 (`Channel._drain`):

1. 대기열이 비어 있지 않으면 **곧바로 민다.** 아무도 밀고 있지 않으면 부르는
   쪽이 그 자리에서 민다.
2. 이미 누가 밀고 있으면 `append()` 는 **기다리지 않고 돌아온다.** 그 건은
   대기열에 쌓인다.
3. 밀던 쪽은 자기 push 가 끝나면 그 사이 쌓인 것을 **한 커밋으로** 또 민다.
   대기열이 비면 멈추고, 다음 `append()` 가 다시 깨운다.

그래서 묶음 크기가 **부하에 맞춰 저절로** 정해진다 — 원격이 느리면 크게 묶이고
(커밋 폭증은 여전히 안 생긴다), 빠르면 지연이 그만큼 작아진다. **조율할 숫자가
없다.** ⚠️ 디바운스가 아니다: 새 건마다 타이머를 리셋하면 빨리 연속으로 치는
사람의 말이 손을 멈출 때까지 안 나간다.

실측 (로컬 bare 원격 · 같은 방법으로 전/후, 5회 중앙값):

| | 한 건 전송 (append → 착지) | push 중 들어온 3건 |
|---|---|---|
| 창 3초 (전) | **4,018 ms** | 커밋 2개 |
| 드레인 루프 (후) | **968 ms** | 커밋 2개 (1건 + 3건이 한 커밋) |

한 커밋으로 나가는 건들의 시각은 **그 커밋이 나가는 시점** 기준이고, 같은
밀리초가 되지 않게 1ms 단위로 증가시킨다 (그래야 발행 순서 = ID 정렬 순서다).

* `append(flush=True)` / `flush()` = **이 건이 나갈 때까지 기다린다.** CLI 처럼
  곧 끝나는 프로세스가 쓴다.
* `Channel(autopublish=False)` = 쌓아 두고 호출자가 `flush()` 로 정한다
  (배치 발행·테스트용). 그 경우 배경 스레드가 아예 뜨지 않는다.
* `max_batch`(기본 200) 는 **발행 트리거가 아니라 한 커밋의 상한**이다.
  초과분은 기다리지 않는다 — 다음 회차가 곧바로 가져간다.
* push 가 실패하면 예외가 호출자에게 올라가고(조용히 삼키지 않는다) 대기열은
  그대로 남아 **배경 재시도**가 이어받는다. 그 재시도 간격만 유일한 타이머이며,
  대기열이 비면 타임아웃 없이 신호를 기다린다.

### 공통 시계 — 로컬 시계를 믿지 않는다

파일명·타임스탬프를 작성자 로컬 시계로 찍으면 참가자 간 시계 차이로 순서가
뒤집힌다. 실측: `curl -sI https://github.com` 의 `Date` 헤더 vs 로컬 시계 =
**2.1초 차이**.

그래서 **이미 통신하고 있는 git 호스트의 HTTP `Date:` 응답 헤더**를 기준으로
오프셋을 구한다. 외부 의존이 0이고(NTP·추가 서비스 불필요), 모든 참가자가 같은
호스트를 보므로 자동으로 공통 기준이 된다.

* `Date` 는 **초 단위 절삭**이라 참값은 `[D, D+1)` 에 균등분포한다 → 점추정은 `D+0.5`.
* 요청 직전/직후 로컬 시각의 **중점**을 서버 시각에 대응시켜 RTT/2 를 상쇄한다.
* 잔여 오차는 대략 ±(0.5 + RTT/2)초.
* **세션 시작 1회 + 15분마다 재측정.** 하드웨어 드리프트는 15분에 수 ms 수준이라
  주기 자체는 여유롭지만, NTP 점프·서스펜드 복귀 같은 계단형 변화는 언제든
  생기므로 "1회 측정 후 영구 사용"은 위험하다.
* 측정 실패는 **치명적이지 않다** — 오프셋 0(로컬 시계)으로 degraded 동작한다.
  시계 보정 실패로 전송이 멈추면 안 된다.

### 다중 채널 폴링 — 채널당 독립 스레드

`ls-remote` 비용은 CPU 가 아니라 **네트워크 왕복 대기**다. 순차로 돌리면
채널 20개에 한 라운드 13초(30초 주기의 절반)를 대기로 태우고, 한 호스트가
느려지면 뒤의 모든 채널이 함께 밀린다(head-of-line blocking).

그래서 **채널마다 독립 폴링 스레드**를 쓴다. git 은 subprocess 라 대기 중 GIL 을
잡지 않으므로 파이썬 스레드로도 실제 병렬 왕복이 된다. 채널 하나 안에서는 같은
작업 사본을 만지므로 락으로 직렬화한다 — 병렬성은 **채널 간**에만 준다.

일회성 소비자(`Hub.fetch_new_all()`, CLI)는 반대로 **순차**다. 한 번 실행하고
끝나는 프로세스에서는 스레드 기동·정리 비용이 이득보다 크다.

### 부분 클론(`--filter=blob:none`)을 쓰지 않는 이유 — 측정 결과

"첫 클론이 과거 blob 을 전부 받는다"는 지적은 맞다. 그래서 부분 클론을 재 봤고,
**넣지 않기로 했다.** 근거(이 머신, 레코드 5000건 방, 로컬 `file://` 원격):

| 방식 | 클론 시간 | 받은 오브젝트 | 팩 크기 |
|---|---|---|---|
| 전체 클론 (지금) | 2807 ms | 5012 | 908 KiB |
| `--filter=blob:none` | 3593 ms | **5012** | 909 KiB |
| `--filter=blob:none --no-checkout` | 395 ms | 8 | 156 KiB |

* **그냥 `--filter=blob:none` 은 아무것도 아끼지 못한다.** 레코드는 전부 HEAD 에
  살아 있으므로 **체크아웃이 그 blob 을 도로 다 받는다.** 왕복만 늘어 더 느렸다.
* 아끼려면 `--no-checkout`(작업 트리 없음)까지 가야 하는데, 그러면 레코드를 읽을
  때마다 promisor 지연 로드가 걸린다. 같은 방에서:

| 읽기 | 시간 |
|---|---|
| 전체 클론, 작업 트리에서 최근 50건 | 2.6 초 |
| 부분 클론, `git show` 로 50건 | 17.5 초 |
| 부분 클론, `cat-file --batch` 로 50건 | 13.4 초 |
| 부분 클론, 전량 5000건 | **23 분** |

  즉 **클론에서 아낀 2.4초를 첫 화면에서 11초 더 내고 갚는다.** 채팅은 결국 그
  레코드들을 읽는 소비자라 이 교환이 성립하지 않는다.
* `--depth`(shallow)는 아예 다른 이유로 안 된다 — 과거를 못 읽으면 역방향
  페이징·무한 스크롤이 성립하지 않는다. (옵션으로는 남아 있다: 읽기를 포기하고
  최신만 보겠다는 소비자를 위해서다.)

**언제 다시 볼 것인가**: 부분 클론이 이기려면 "필요한 만큼만, **한 번의 왕복으로**"
받아야 한다. 우리 레코드는 날짜 디렉토리로 샤딩돼 있으니
`sparse-checkout` 을 날짜 단위로 넓히면(=페이지 한 쪽 = 왕복 한 번) 성립할 수 있다.
다만 그건 작업 트리를 전제로 한 append·rebase·compact 경로를 전부 다시 짜는 일이라
지금 넣지 않는다. 넣는다면 그때도 **측정부터** 한다.

### 클론 위치

사용자가 볼 일이 없는 앱 상태 저장소다. OS 관례를 따른다:

| OS | 위치 |
|---|---|
| Windows | `%LOCALAPPDATA%\gitwire\channels\<slug>-<hash12>\` |
| macOS | `~/Library/Application Support/gitwire/channels/...` |
| Linux | `$XDG_DATA_HOME`(기본 `~/.local/share`)`/gitwire/channels/...` |

**캐시가 아니라 데이터 디렉토리를 쓴다** — 커서와 아직 push 되지 않은 레코드가
여기 있어서, 캐시 청소 도구가 지워도 되는 데이터가 아니다. 디렉토리 이름은
정규화한 URL의 `sha256` 앞 12자리에 사람이 알아볼 slug 를 붙인 것이라,
**같은 URL 이면 어느 프로세스에서 열든 같은 클론·같은 커서**를 가리킨다
(그래서 일회성 CLI 호출을 반복해도 상태가 이어진다). `GITWIRE_HOME` 으로
통째로 덮어쓸 수 있다.

### 자격증명

* **채널마다 다른 토큰**을 줄 수 있다(다른 조직 레포). 전역 하나로 두면 막힌다.
* 값은 **로컬 프로세스 안에만** 있는다. gitwire 는 토큰을 저장하지 않는다 —
  저장 책임은 호출자(환경변수·OS 키체인·시크릿 매니저)에게 있다.
* URL 에 토큰을 박지 않는다(`.git/config` 에 평문으로 남는다). `GIT_ASKPASS`
  헬퍼 + 환경변수로 넘긴다 — 프로세스 인자(`ps` 노출)에도 git config 에도
  남지 않고, 헬퍼 스크립트 파일 자체에도 토큰이 없다.
* 로그·예외·반환값에 절대 싣지 않는다. 모든 git 출력은 레닥션을 거친다.

### 지난 날짜 아카이빙 — 하루치를 **로컬 파일 1개**로 옮긴다 (레코드 삭제는 합의 뒤)

레코드 1건 = 파일 1개다. 활발한 방은 하루 수백 건이 쌓인다. **먼저 무엇이 아픈지
재고 시작했다.**

**읽기 속도는 문제가 아니다.** 위 「역방향 페이징」 + 「나열 캐시」 덕에 페이지
조회는 규모와 무관하게 평평하다 (아래 표의 `페이지 조회` 행 — 500건이나 45,000건이나
같다). 아픈 것은 **파일 개수 그 자체**다: 클론 후 체크아웃, 레코드를 발행할 때마다
도는 `git add -A -- records`, 작업 트리의 파일 수. 윈도우 파일시스템은 작은 파일
수만 개를 특히 싫어한다.

측정 환경: Windows 11 · git 2.51 · Python 3.14 · 로컬 `file://` 원격
(네트워크 왕복을 빼고 **git 자체와 파일시스템 비용만** 남긴 값이다).
방은 하루 500건 × N일, 레코드 3건당 1커밋으로 만들었다.

| 항목 | 1일x500 전 → 후 | 7일x500 전 → 후 | 30일x500 전 → 후 | 90일x500 전 → 후 |
|---|---|---|---|---|
| 클론 (전체) | 517ms → **303ms** | 2.1s → **513ms** | 8.3s → **1.4s** | 23.9s → **3.7s** |
| 클론 (`--depth 1`) | 564ms → **246ms** | 2.3s → **390ms** | 8.7s → **1.1s** | 24.9s → **2.1s** |
| 체크아웃 | 353ms → **48ms** | 2.2s → **60ms** | 8.9s → **87ms** | 27.1s → **165ms** |
| `git add -A -- records` (발행마다) | 71ms → **48ms** | 111ms → **54ms** | 92ms → **53ms** | 147ms → **87ms** |
| `git status` | 76ms → **49ms** | 106ms → **62ms** | 84ms → **54ms** | 126ms → **81ms** |
| `ls-tree -r records/` | 52ms → **48ms** | 55ms → **52ms** | 61ms → **50ms** | 96ms → **48ms** |
| 작업 트리 파일 수 | 504 → **5** | 3,504 → **11** | 15,004 → **34** | 45,004 → **94** |
| git 오브젝트 수 | 1,175 → **1,179** | 8,183 → **8,193** | 35,047 → **35,080** | 105,127 → **105,220** |
| pack 크기 | 0.2MB → **0.2MB** | 1.4MB → **1.6MB** | 6.1MB → **6.8MB** | 18.4MB → **20.5MB** |
| 커밋 수 | 168 → **169** | 1,170 → **1,171** | 5,011 → **5,012** | 15,031 → **15,032** |
| 페이지 조회 (50건) | 55ms → **52ms** | 59ms → **52ms** | 53ms → **55ms** | 52ms → **57ms** |
| 10쪽 스크롤 (500건) | 657ms → **552ms** | 708ms → **593ms** | 720ms → **607ms** | 691ms → **574ms** |
| 읽히는 레코드 수 | 500 → **500** | 3,500 → **3,500** | 15,000 → **15,000** | 45,000 → **45,000** |

⚠️ 이 표의 **`pack 크기` 행은 아카이브를 커밋하던 옛 방식**에서 잰 값이다. 바로
그 행이 설계를 바꾼 이유이고, 아래에서 그것을 다룬다. 나머지 행(파일 개수·클론·
체크아웃·조회)은 지금도 그대로 성립한다 — 줄어드는 것은 HEAD 트리 이후의 모든
것이고, 실측에서 그게 클론 시간까지 지배했다 (90일 방의 `git clone` 23.9초 →
3.7초 — 체크아웃이 27초에서 0.17초로 없어졌기 때문이다).

#### ⚠️ 설계가 한 번 바뀌었다 — 아카이브를 **커밋하지 않는다**

위 표를 처음 냈을 때 우리는 아카이브 파일을 **커밋했고**, 같은 커밋에서 그 날의
레코드를 지웠다. 그때 정직하게 적어 둔 한 줄이 이렇다: *"커밋 수는 그대로이고
**pack 은 오히려 커진다**(18.4MB → 20.5MB, +11%)."*

그 +11% 의 정체는 **같은 데이터가 두 벌 저장된 것**이다. 삭제된 레코드 blob 은 옛
커밋에서 계속 도달 가능하므로 히스토리에 영구히 남고, 그 옆에 같은 바이트의 아카이브
blob 이 새로 추가된다. 작은 실제 레포에서 재측정한 값 — 롤업 커밋이 추가한 아카이브
blob **5,515 바이트** = 직전 커밋의 레코드 blob 합계 **5,515 바이트**. 즉 정확히
한 벌이 더 쌓인 것이고, "롤업이 용량을 줄인다"는 말은 **틀렸다.**

그래서 두 가지를 바꿨다:

1. **아카이브는 추적하지 않는다 (`archive/` 를 gitignore).** 각자의 작업 사본에만
   있는 로컬 파일이다. `.gitignore` 자체는 **커밋한다** — 전원이 무시해야 하므로.
2. **레코드 삭제는 "전원이 그 날짜를 자기 로컬 아카이브로 옮겼다"고 확인응답한
   뒤에만** 일어난다. 그 판정은 **소비자**의 일이고(참가자 상태 파일 안의 소비자
   스키마다 — `participants/`), 기반은 *아카이빙*과 *삭제*를 **두 동작으로 분리해**
   내준다:

       ch.archive_days()         # 로컬 파일로 옮긴다 (커밋·push·네트워크 0, fsync)
       ch.drop_days(days)        # 그 날짜의 레코드만 지운다 (커밋 1개 + ff push)
       ch.recover_archive(day)   # 지워진 날짜를 히스토리에서 꺼내 아카이브를 채운다

남는 이득은 위 표의 **파일 개수·체크아웃·클론**이고(그게 진짜 비용이었다), 잃었던
+11% 는 이제 늘지 않는다.

#### 형식 — `archive/<YYYYMMDD>.jsonl`, 레코드 한 건 = 한 줄 (**추적되지 않는다**)

    archive/20260901.jsonl
    {"gitwire":1,"id":"records/20260901/...json","sender":"...","ts":"...","payload":{...}}
    {"gitwire":1,"id":"records/20260901/...json",...}
    ...                          ← 레코드 **id 오름차순**, UTF-8(BOM 없음)·LF

**왜 JSON Lines 인가 — 합집합이 자연스럽게 정의되기 때문이다.**

* **한 레코드 = 한 줄** → 두 아카이브의 **합집합이 줄 집합의 합집합**이다. 아카이빙은
  언제나 *기존 로컬 아카이브 ∪ 지금 살아 있는 레코드*로 다시 쓴다. 삭제 뒤에는 로컬
  아카이브가 **유일한 사본**이므로, 다시 쓸 때 기존 줄을 잃으면 그 순간이 유실
  지점이다. 통짜 JSON 배열 하나였다면 합치려고 전체를 파싱해 다시 써야 한다.
* **id 오름차순 정렬** → id 는 고정폭 타임스탬프로 시작하는 유일 키라 전순서가
  결정된다. 순서가 결정적이어야 바이트가 결정적이다.
* 레코드 파일의 바이트를 **그대로** 한 줄로 옮긴다(재직렬화하지 않는다).
* 개행 LF, 끝줄에도 개행 하나, UTF-8(BOM 없음).

바이트가 결정적인 성질은 이제 "동시 롤업 수렴"의 근거가 아니다(아카이브는 공유되지
않는다). 그래도 유지한다 — **재실행이 멱등**해지고(합친 바이트가 파일과 같으면 아예
쓰지 않는다 → mtime 이 흔들리지 않아 캐시가 유지된다), 두 참가자의 로컬 아카이브를
바이트로 비교해 진단할 수 있다.

#### 레코드 id 는 바뀌지 않는다

id = `records/<날짜>/<타임스탬프>-<sender>-<nonce>.json` 이고 그것이 곧 **정렬 키·
`before=` 커서·소비자 커서·답장 대상**이다. 아카이빙은 **저장 위치만 바꾸고 id 는
데이터로 보존한다** — 봉투 안의 `"id"` 가 원본 그대로다. 읽기 경로는 id 를

1. 살아 있는 파일 → 2. **로컬** 아카이브 안의 한 줄 → 3. 지금 트리의 git 오브젝트
   → 4. **그 레코드를 추가한 커밋**(히스토리)

순으로 해결한다. 4번이 마지막 안전망이다 — 어디에도 없는 id 를 조용히 "없다"로
넘기지 않는다. 소비자는 어느 쪽인지 알 필요가 없고, 디스크에 이미 영속된 커서도
그대로 유효하다.

**페이징은 아카이브를 투명하게 가로지른다.** 날짜 축(`_day_index`)에 산 날짜와 옮긴
날짜가 함께 올라가고, 아카이브 파일은 **그 날짜를 실제로 방문할 때 하루치 한 파일만**
연다. 날짜가 곧 파일명이므로 예전의 `ls-tree` 조회는 `scandir` 한 번(git 0개)으로
대체됐다. 캐시 열쇠는 blob sha 대신 **mtime+크기**다 — 이 파일을 쓰는 것은 본인
프로세스 하나(원자적 교체)라 "같은 나노초·같은 크기로 다른 내용"이 생기지 않는다.
(자체 해시를 새로 만들지 않는다. 그건 손상 검증이고, 우리에게 필요한 것은 캐시
열쇠다 — 파일 전량 읽기는 캐시가 없애려던 비용 그 자체다.)

#### 배치 **시각**과 "어제"의 **정의**는 다른 것이다

* **실행 시각**은 소비자가 정한다 (gitwire-chat 은 각자 **로컬 04:00**). 참가자마다
  시간대가 달라도 상관없다 — **삭제는 합의 뒤**라 시각을 맞출 필요가 없다.
* **"어제"의 정의는 UTC 날짜다.** 날짜 디렉토리 이름 자체가 UTC 날짜이고
  (`format_ts`), 로컬 시각으로 날짜를 계산하면 폴더명과 어긋난다. 판정은 기반이
  내준다 — `is_closed()` · `last_closed_day()` · `today_utc()`.

유예 2시간이 사는 것은 **참가자 간 시계 오차**(gitwire 는 git 호스트의 HTTP `Date`
로 시계를 맞춰 잔여 오차가 초 단위지만, 보정에 실패한 참가자는 로컬 시계로 degraded
동작한다)와 **발행 배칭·push 지연**이다. 그보다 늦게 오는 것은 지연이 무한할 수 있어
**유예로 막을 수 있는 성질이 아니다** — 그건 아래 「뒤늦게 도착한 레코드」로 따로
처리한다.

한국 시간으로 읽으면 UTC 날짜 D 는 **KST D+1 오전 11시** 이후 "지난 날"이 된다.

#### 유실 금지 — 다섯 가지 장치

1. **옮기기가 끝난 뒤에 확인응답한다 (순서).** `archive_days()` 는 임시 파일에 쓰고
   `fsync` 로 디스크에 내려보낸 뒤 원자적으로 교체하고 돌아온다. 소비자는 **그
   뒤에만** "여기까지 옮겼다"를 발행한다. 반대로 하면 응답만 보내고 죽었을 때 남들이
   레코드를 지우고 **그 사람만 잃는다.**
2. **옮기지 못한 날이 있으면 워터마크가 그 앞에서 멈춘다.** 건너뛰고 올리면 그 날의
   레코드가 내 아카이브에 없는데도 남들이 지울 수 있다. (한 날짜가 계속 실패하면
   그 뒤의 삭제가 전부 멈춘다 — **안전측 정지**이고, 소비자가 사람에게 알린다.)
3. **내가 담지 않은 레코드는 지우지 않는다.** `drop_days()` 는 지우기 직전에 그
   날짜를 한 번 더 아카이빙(합집합·멱등)하고, 살아 있는 레코드 전부가 내 로컬
   아카이브에 있는지 확인한다. 하나라도 없으면 그 날짜를 건너뛴다. 접을 수 없는
   바이트(`.json` blob 이 아닌 항목·봉투로 해석되지 않는 레코드)가 섞여 있으면
   **그 날짜를 통째로** 건너뛴다.
4. **fast-forward push 만 한다.** 삭제 커밋은 임시 인덱스 + `commit-tree` 로
   만들어(작업 사본·진짜 인덱스·현재 브랜치를 한 바이트도 건드리지 않는다) 부모가
   그대로일 때만 통과한다. *내가 못 본 레코드가 원격에 있으면 push 자체가 거부된다.*
5. **삭제는 되돌릴 수 있다.** 평범한 커밋이라 지워진 레코드가 히스토리에 그대로
   남는다. `recover_archive(day)` 가 *그 날짜를 지운 커밋들의 부모*에서 원본을 꺼내
   로컬 아카이브에 **합집합으로** 채운다. 히스토리가 없으면(shallow·`compact()` 이후)
   조용히 넘기지 않고 `problems` 로 돌려준다.

#### 동시 삭제 — 조정하지 않는다

락 파일도, 리더 선출도, "누가 지울지 정하기"도 없다. 필요가 없기 때문이다. 두 사람이
같은 날짜를 동시에 지우려 하면 한쪽 push 가 거부되고, 진 쪽은 pull 하면 **이미 지워져
있어** 할 일이 없어진다. 이미 있던 "push 거부 → fetch → 재시도" 결을 그대로 따른다.

#### 뒤늦게 도착한 과거 레코드

**경로가 하나로 줄었다.** 시각은 push 되는 순간에 찍히므로(위 「레코드의 시각·ID」)
*오프라인에서 쓰고 나중에 push* 는 더는 과거 날짜를 만들지 않는다. 남은 것은
**시계가 어긋난 *다른* 참가자** 하나다. 그 경우 이미 옮긴(또는 이미 지워진) 날짜에
라이브 레코드가 새로 생긴다.

* 읽기: 날짜 축이 **라이브 ∪ 로컬 아카이브**를 돌려준다 → 곧바로 보이고, id 순서가
  맞고, 중복이 없다. **이 합집합을 없애면** 삭제 뒤에 늦게 온 레코드 하나 때문에
  그 날의 나머지 대화가 화면에서 통째로 사라진다 (라이브만 보게 되므로).
* 다음 아카이빙: 합집합으로 다시 쓴다. **"그 날은 이미 닫혔다"고 버리지 않는다.**
* 이미 응답한 뒤에 도착했다면 내 아카이브가 **불완전**할 수 있다 — 그래서 소비자는
  삭제를 관찰할 때마다 `recover_archive()` 를 부른다(합집합이라 멱등하고, 완전하면
  아무것도 쓰지 않는다).

#### 소비자가 삭제를 건너뛰지 않는 법

여기가 가장 조용히 틀릴 수 있는 자리였다. 커서는 `base..target` **diff** 로 새
레코드를 찾는데, 삭제 커밋이 범위 안에 있으면 *그 사이에 추가됐다가 지워진* 레코드는
diff 에 **아예 나타나지 않는다**(두 트리의 차이에서 추가와 삭제가 상쇄된다). 주말
내내 앱을 꺼 뒀다가 켜면 주말 대화가 통째로 사라지는 모양이다. 실측으로 확인했다 —
옛 방식(`git diff base target -- records/`)은 add+delete 된 레코드를 내지 못한다.

그래서 트리의 차이가 아니라 **범위 안의 커밋들이 실제로 추가한 경로**를 묻는다:

    git log --diff-filter=A --name-only --pretty=format: -z base..target -- records/

상쇄가 정의상 일어나지 않고, git 호출도 (diff 두 번 대신) **한 번**이다. 예전에는
추적되던 `archive/` 의 집합 차이로 이 구멍을 메웠는데, 그 보험은 없어졌다 — diff 할
아카이브가 없고, 애초에 **핸드셰이크가 더 강한 보장을 준다**(삭제는 전원이 옮긴 뒤에만
오므로 삭제가 도착할 때 그 레코드는 이미 내 디스크에 있다).

⚠️ **정직하게 밝혀 둘 한 가지 — 갓 합류한 사람이 보는 것.** 아카이브가 공유되지
않으므로, 이미 지워진 날짜는 새 클론의 날짜 축에 **없다**(살아 있는 날짜만 있다).
그 대화는 히스토리에 그대로 있고, `archive_gaps()` 로 빈 날짜를 찾아
`recover_archive()` 로 꺼내면 돌아온다 — gitwire-chat 은 기동 직후 첫 배치에서 그것을
한 번 훑는다(기본 60일). 사라진 것이 아니라, **꺼내는 자리가 있다.**

#### 비동기 — 아카이빙이 도는 동안 읽기·쓰기가 막히지 않는다

* `poll_once()` 가 매 틱 **캐시된 나열 1회**로 후보만 본다(레코드 blob 을 열지
  않는다). 이미 옮긴 뒤 트리가 바뀌지 않은 날짜는 후보가 아니다 → 합의를 기다리는
  동안 같은 날짜를 매시간 다시 옮기지 않는다. 후보가 없으면 스레드조차 만들지 않는다.
* 후보가 있으면 **배경 스레드**로 나간다. 자동 경로가 하는 일은 **로컬 파일 쓰기뿐**
  이다 — 커밋도 push 도 네트워크도 없다. 그래서 켜 두어 잃는 것이 없고(소비자의 일일
  배치가 멈춰 있어도 로컬 아카이브는 만들어져 있다), **레코드 삭제는 절대 자동이
  아니다.**
* **빈도**: 기본 1시간마다 확인. 옮길 수 있는 날짜가 늘어나는 사건은 하루 한 번
  (UTC 자정 + 유예)뿐이라 그보다 자주 볼 이유가 없고, 확인 비용이 사실상 0이라
  더 드물게 볼 이유도 없다. 끄려면 `auto_archive=False` 또는
  `GITWIRE_AUTO_ARCHIVE=0`.
* 실패해도 앱이 죽지 않는다. **조용히 넘어가지도 않는다** — 로그에 예외를 남기고
  `info()["archive_error"]` 로 드러나며, 다음 기회에 다시 시도한다.

삭제 쪽의 비용은 **로컬 통합 한 번**이다(작업 사본에서 그날 파일 수백 개를 지우는
checkout). 실측(하루 120건 × 4일 = 480건을 옮기고 지우는 동안, 같은 클론에서 읽기를
쉬지 않고·쓰기를 20ms 간격으로 계속하면서) 읽기·쓰기는 그 내내 계속 완료됐고, 어느
한 호출도 전체를 기다리지 않았다 (`tests/test_archive.py::
test_archiving_does_not_block_reads_and_writes` 가 시간으로 못 박는다). 이건 아카이빙
고유의 비용이 아니라 `sync()` 가 원격 변경을 받을 때마다 하는 일과 같은 것이고,
**하루 한 번**이며, 그 대가로 이후의 모든 `git add -A`·`status`·체크아웃이 위 표만큼
싸진다.

#### 하위호환 — 이 설계를 모르는 옛 버전이 같은 방에 붙으면

* **레포에서 사라지는 것은 없다.** 지워진 레코드는 옛 커밋 안에 그대로 있다
  (히스토리 재작성이 아니므로 `git log -p` 로도 전부 나온다).
* 옛 버전(추적되는 아카이브를 만드는 v0.2.0 이하)은 **자기 아카이브를 커밋한다.**
  `.gitignore` 는 추적 중인 파일에 영향이 없으므로 그 파일은 계속 추적된다. 그것이
  이 설계가 고치려던 이중 저장이므로, **같은 방에 옛 버전이 남아 있으면 먼저 올려라.**
  이미 추적되고 있는 아카이브 파일은 **사람이 직접** 정리한다(`git rm --cached`) —
  gitwire 는 남의 레포에서 파일을 지우지 않는다.
* 옛 버전은 **지워진 날짜를 `history()` 에서 보지 못한다.** 그 날짜 디렉토리가 사라진
  것으로 보인다. 오류는 나지 않는다.
* 옛 버전이 **뒤처진 상태에서** 삭제를 만나면, 그 사이에 지워진 레코드를 자기 콜백으로
  전달하지 못한 채 커서가 지나간다(위 「소비자가 삭제를 건너뛰지 않는 법」이 옛 코드에는
  없다). **되돌릴 수 있다** — gitwire 를 올린 뒤 그 소비자의 커서
  파일(`cursors/<소비자>.json`)을 지우면 다시 읽는다.
* 옛 버전이 발행·push 하는 것은 아무 영향이 없다(라이브 파일로 들어오고, 다음
  아카이빙이 흡수한다).

### 히스토리 관리 — v1 범위

커밋은 계속 늘어난다. 하지만 **git 히스토리 자체는 이 서비스에 중요하지 않다 —
레코드 파일이 곧 기록이다.** 두 수단을 제공한다:

1. **shallow clone** (`depth=N` / `--depth N`) — 옵트인이지만 **안전한 쪽**이다
   (기본값은 전체 클론). 파괴적이지 않고 내 로컬 비용만 줄인다 — 다른 참가자에게
   아무 영향이 없다. 다만 조상 관계를 로컬에서 판정할 수 없으므로 "여기까지
   push 됨"을 로컬 ref(`refs/gitwire/pushed`)로 따로 표시해 미푸시 여부를 판단한다.

2. **지난 날짜 아카이빙 + 삭제**(`archive_days()`/`drop_days()` /
   `gitwire archive [--drop]`) — 위 절 참조. **비파괴다** (아카이빙은 로컬 파일,
   삭제는 평범한 커밋 1개·force-push 없음, 레코드는 히스토리에 남는다). 아카이빙만
   기본으로 배경에서 돌고 **삭제는 소비자가 합의를 확인한 뒤에만** 시킨다.
   커밋 수를 줄이지는 않고, **파일 수**를 줄인다.

3. **압축**(`compact()` / `gitwire compact --yes`) — 최근 N건만 남긴 단일
   커밋으로 재작성 후 force-push. **파괴적이다.** ⚠️ **아카이빙과 정반대**다 —
   아카이빙은 옮기고(히스토리에 원본이 남는다), 압축은 **버린다**. 압축은 로컬
   `archive/` 를 건드리지 않지만, **히스토리를 지우므로 `recover_archive()` 의
   원본도 함께 사라진다** — 아카이브가 없는 참가자는 그 대화를 되찾을 수 없다.

   압축의 위험은 "다른 참가자의 미푸시 레코드가 날아간다"는 것이다. 이렇게 다룬다:

   * **자동·주기 실행 경로를 아예 두지 않았다.** `confirm=True`(CLI 는 `--yes`)
     없이는 호출 자체가 거부된다. v1 에서 압축은 **사람이 의도적으로 부르는 도구**다.
   * 압축하는 쪽은 자기 미푸시분을 먼저 flush 한다.
   * 재작성을 만난 다른 참가자는, 미푸시 커밋이 없으면 조용히 `reset` 해서
     따라가고, **미푸시 커밋이 있으면 그것만 새 히스토리 위로 옮겨 심는다**
     (`rebase --onto`). 레코드가 서로 다른 파일이라 충돌이 없다.
   * 그마저 불가능하면 **말없이 버리지 않고** `HistoryRewritten` 을 올린다.
     사람이 `flush()` 하거나 `recover(discard_local=True)` 를 명시적으로 부르게 한다.

   즉 v1 의 입장은 "압축은 제공하되 기본값은 아니다. 자동으로 남의 데이터를
   지우는 경로는 만들지 않는다"이다.

## 정직한 한계

이 설계가 **못 하는 것**들이다. 소비자를 만들기 전에 반드시 읽어라.

* **실시간이 아니다.** 지연 = 폴 주기다. 기본 30초면 최악 30초 + pull 시간이
  걸린다. 주기를 줄이면 그만큼 요청이 늘어난다(호스트 rate limit 주의).
* **진짜 push 가 없다.** 서버가 우리를 깨워주지 않는다. 전부 폴링이다.
  "새 메시지 알림"류는 이 위에서 폴 주기만큼 늦게 뜬다.
* **히스토리가 계속 늘어난다.** 레코드마다 커밋이 쌓인다. 지난 날짜 아카이빙은
  **파일 수**를 줄이지만 **커밋 수와 pack 크기는 줄이지 않는다**(비파괴의 대가다 —
  옛 blob 이 옛 커밋에서 계속 도달 가능하다). 다만 아카이브를 커밋하지 않게 바꾼
  뒤로는 **더 늘지도 않는다**(예전에는 같은 데이터가 두 벌 쌓여 +11%였다). 전송량까지
  줄이려면 `depth=1` 을 함께 쓰거나, 파괴적인 압축을 명시적으로 불러야 한다.
* **이미 지워진 날짜는 갓 합류한 사람의 날짜 축에 없다.** 아카이브가 공유되지
  않기 때문이다. 히스토리에는 그대로 있고 `archive_gaps()`+`recover_archive()` 로
  꺼낼 수 있다(소비자가 기동 직후 훑는다, 기본 60일). 그보다 오래된 날짜는 히스토리가
  있어야 꺼낼 수 있다 — `compact()` 를 부른 방이라면 꺼낼 원본이 없다.
* **처음 합류할 때 과거 레코드를 전부 받는다.** 부분 클론으로 줄여 보려 했지만
  측정 결과 이 workload 에서는 손해였다(위 「부분 클론을 쓰지 않는 이유」).
  읽기가 O(요청 건수)인 것과 별개로, *받는 것*은 여전히 전량이다.
* **레포 접근권 = 참여권이다.** per-record ACL 이 없다. 레코드 하나만 가리거나
  "이 시점부터만 보여주기"가 불가능하고, 나중에 합류한 참가자는 과거 레코드를
  전부 본다 (git 히스토리를 그대로 쓰는 구조의 귀결이다).
* **레코드 삭제가 사실상 안 된다.** append-only 다. 지우려면 히스토리 재작성
  (압축)이 필요하고 그건 모든 참가자에게 파괴적이다.
* **참가자 수가 늘면 push 경합이 커진다.** 선점 시 rebase 후 재시도하므로
  정확성은 유지되지만, 동시 발행이 잦을수록 재시도가 늘어난다. 수십 명이 초 단위로
  쏟아붓는 용도는 아니다.
* **참가자 사이의 순서는 시계 보정 오차만큼 흔들린다.** 타임스탬프 자체는
  **밀리초** 해상도이고(`records.format_ts`), 한 발신자가 낸 레코드들은 그
  해상도로 시간순이다(같은 밀리초에 두 건을 내면 아래 ID 규칙으로 갈린다). 뒤집힐 수 있는 것은 **서로 다른 참가자가 거의 동시에
  발행했을 때**뿐이다 — 공통 시계의 잔여 오차가 대략 ±(0.5 + RTT/2)초이기 때문이다
  (HTTP `Date` 가 초 단위로 절삭되는 것은 *오프셋 추정*의 한계이지 스탬프의
  정밀도가 아니다). 타임스탬프까지 같으면 레코드 ID 로 갈리고, 그 순서는 ID
  사전식 정렬이라 **모든 참가자에게 동일**하다 — 즉 전역 전순서를 보장하지는
  않지만 읽는 쪽마다 다르게 보이지도 않는다.
* **아직 push 되지 않은 발행은 프로세스와 함께 사라진다.** 대기열은 메모리다
  (위 「레코드의 시각·ID」). 강제 종료·전원 뽑기에서 안 나간 것은 복구되지 않는다 —
  시각을 push 시점으로 옮기기 위해 **의도적으로** 포기한 보장이다. 소비자는 안 나간
  것을 "보냈다"로 표시하지 말아야 한다(그래야 사라져도 거짓말이 되지 않는다).
  정상 종료 경로에서는 `close()` 가 마지막으로 한 번 밀어낸다.
* **크래시 시점에 따라 재전달이 있을 수 있다.** 커서는 콜백이 성공한 **뒤에**
  저장된다. 콜백 실행 도중 프로세스가 강제 종료되면 그 한 건이 다음 실행에서
  다시 온다. 소비자 쪽 처리는 **멱등(idempotent)** 하게 만들어라.
* **내용 검색은 레코드를 읽어서 한다.** 인덱스를 두지 않았다 — 페이징은 ID 만으로
  되지만(O(요청 건수)) payload 안을 찾는 일은 파일을 여는 수밖에 없다. 아주 큰
  채널에서 잦은 검색이 필요하면 소비자가 자기 인덱스를 만들어야 한다.
* **참가자 상태는 마지막 값만 남는다.** `participants/` 는 덮어쓰는 경로다 —
  변경 이력이 필요하면 그건 사건이므로 레코드로 적어야 한다. 그리고 "누가 자기
  파일에만 쓰는가"를 기반이 강제하지 않는다 (신원 검증 수단이 없다 — 레포 접근권이
  곧 참여권인 구조의 귀결이다).
* **레코드 크기.** git 이 감당하는 만큼이 한계다. 큰 바이너리는 넣지 마라
  (레포가 영구히 무거워진다).
* **로컬 ref 조회는 `.git` 안 파일이 정본이라고 가정한다.** 유휴 폴링을 git
  1개로 줄이면서 HEAD·원격추적 ref 를 메모리에 들었고, 유효성을 그 파일들의
  스탬프(내용 + stat)로 판정한다 (위 「유휴 폴링」). 사람이 그 클론에서 직접
  git 을 돌리는 경우는 이 방어에 잡힌다 — ref 가 바뀌면 파일이 반드시 바뀐다.
  잡히지 않는 경우는 *ref 파일을 한 바이트도 바꾸지 않으면서 ref 해석이 달라지는*
  경우인데, 우리가 아는 그런 경우는 `reftable` 백엔드 하나이고 **그때는 캐시를
  아예 켜지 않는다**(워크트리·서브모듈 레이아웃도 마찬가지). 즉 대가는 *느려지는
  것*이고 틀리는 것이 아니다. 상태는 `channel.local_ref_cache_info()` 로 본다.

## 개발

```bash
python -m pytest -q
```

핵심 검증은 **로컬 bare 레포를 원격으로 삼은 2-클론 왕복**이다. 대역이 아니라
**실제 git** 으로 돌린다 — push 거부·rebase·`ls-remote` 같은 것들은 흉내내면
아무것도 증명하지 못한다. 네트워크·git 호출은 주입 가능하므로 단위 테스트는
네트워크 없이 돈다.

파일은 UTF-8(BOM 없음)·LF 로 쓴다.
